# Praxis v2 Contract

Praxis v2 is the release where Praxis becomes a minimal Linux distro where the
operator controls the system.

The promise is blunt:

```text
You get an ISO and a hard install environment.
You configure the kernel policy.
You pick the init path.
You choose packages and bundles.
You write or inspect the system contract.
```

Praxis v2 is not for beginners.

## Required Shape

- ISO build path remains owned by Praxis.
- The live environment stays shell-first.
- Kernel choices are inspectable.
- Init choices are inspectable.
- Package bundles and desktop profiles are inspectable.
- Recovery is inspect-only and prints manual ledgers.
- The install path remains explicit and hostile to accidental automation.

## Current Scope

Praxis v2 currently includes:

- `praxis-choice`: inspect kernel, init, desktop, and package choices without
  applying them automatically
- `praxis-seed`: apply or dry-run explicit seed ledgers against a target root
- `config/seeds/*.seed`: explicit seed ledgers for base, workstation,
  recovery, and v2-half flows
- `praxis-manifest`: inspect and verify base-system manifests without
  repairing the target
- `config/manifests/base-system.manifest`: an auditable ledger of the base
  runtime surface Praxis claims to ship
- `praxis-provenance`: inspect build metadata and verify rootfs checksums
- `praxis-pkg`: inspect and validate native `.prx` package metadata, indexes,
  archives, and explicit local installs
- `praxis-contract`: export, inspect, and verify text contract bundles without
  applying them
- `praxis-recover`: inspect a target and print manual recovery commands
- `make v2-check`: validation for most of the v2 contract

## Hard Choice Rule

Praxis is not trying to become an installer that decides the system for you.

You inspect choices:

```bash
praxis-choice list
praxis-choice show kernel tiny
praxis-choice show init busybox
praxis-choice show bundle essentials
```

You can emit a choice file skeleton:

```bash
praxis-choice emit --kernel tiny --init busybox --bundle essentials
```

But Praxis does not install that file for you. The operator writes it where it
belongs:

```bash
mkdir -p /mnt/praxis/etc/praxis
praxis-choice emit --kernel tiny --init busybox --bundle essentials \
  > /mnt/praxis/etc/praxis/system.choice
vi /mnt/praxis/etc/praxis/system.choice
```

That file is a contract, not a wizard result.

Then you validate it and emit boot-entry text yourself:

```bash
praxis-choice validate /mnt/praxis/etc/praxis/system.choice
praxis-choice boot-entry /mnt/praxis/etc/praxis/system.choice
```

`boot-entry` prints a skeleton. It does not write to `/boot`.

`targetcheck` treats `system.choice` as binding when it exists. It checks:

- `KERNEL_ARTIFACT` is catalog-valid and present inside the target
- `KERNEL_CONFIG_FRAGMENT` is catalog-valid and present inside the target
- `INIT_RDINIT` matches the init catalog
- the selected init path exists inside the target
- selected init required files and directories exist inside the target
- boot entries use the selected `rdinit=`
- selected desktop, bundles, and extra packages match
  `/etc/praxis/packages.selected` when package intent is present

For a full v2 audit, run:

```bash
targetcheck --strict /mnt/praxis
```

Strict mode requires `system.choice`, build provenance, rootfs checksums,
base-system manifest verification, package selection metadata, and zero
warnings. It is meant for proving a target, not for guiding the early install
steps.

## Kernel Rule

Kernel profiles live in `config/choices/kernel/`.

They are not magic build buttons. They document the kernel policy the operator
selected. The operator still owns the kernel artifact and boot entry.

If a target contains `/etc/praxis/system.choice`, the selected kernel artifact
and selected kernel profile fragment must exist in the target filesystem.

Profile fragments must use explicit config settings:

```text
CONFIG_EXT4_FS=y
CONFIG_VIRTIO_NET=y
```

Bare symbols are rejected by `make check-kernel-profiles`. Kernel builds write
`kernel/PROFILE.applied` and `kernel/build-info` so the operator can inspect
which profile was actually applied.

## Init Rule

Init choices live in `config/choices/init/`.

Praxis defaults to BusyBox init through `rdinit=/init`, but v2 must make other
init choices explicit. If the operator chooses another init, boot entries and
target contents must agree. `targetcheck` reports mismatches.

Each init profile declares:

- `RDINIT`: the boot command line init path
- `REQUIRED_FILES`: comma-separated files the target must contain
- `REQUIRED_DIRS`: comma-separated directories the target must contain

For example, choosing `s6` means `/sbin/s6-svscan`, `/etc/s6`, and `/service`
must exist in the target. Praxis will not create those paths for you.

### Default Init: BusyBox with a Runit-Style Supervise Tree

`RDINIT=/init` names the boot-cmdline PID 1 program, not everything it does.
Praxis's `/init` (`boot/init`) is intentionally small: it mounts the pseudo
filesystems (`/proc`, `/sys`, `/dev`, `/run`, `/tmp`), handles the
initramfs-to-installed-root `switch_root` handoff, then execs BusyBox
`runsvdir` over `/etc/service`. Everything after that point is real service
supervision, not inline shell logic in PID 1.

`runsvdir` scans `/etc/service/*` and starts a `runsv` supervisor for each
service directory it finds. Each service directory needs one executable
file: `run`. `runsv` execs it, and if it exits, `runsv` starts it again —
so a `run` script should `exec` its real long-running process rather than
forking and returning, matching how any runit-family init expects services
to behave.

The `busybox` init profile's `REQUIRED_FILES`/`REQUIRED_DIRS` reflect this:
`/etc/service/shell/run` and the `/etc/service` directory itself are part of
what BusyBox init actually requires to boot to a usable state, not just
`/init` and `/bin/busybox`.

Service definitions and enable state are split, following runit's own
convention:

- `/etc/sv/<name>/` is the source of truth — every known service lives
  here, whether enabled or not. `runsvdir` never scans this directory
  directly.
- `/etc/service/<name>` is a symlink to `../sv/<name>`, present only when
  that service is enabled. This is what `runsvdir` actually supervises.

`praxis-sv` manages that symlink:

```bash
praxis-sv list                    # every known service under /etc/sv
praxis-sv status                  # enabled/disabled state of each
praxis-sv enable <name>           # symlink /etc/service/<name> -> ../sv/<name>
praxis-sv disable <name>          # remove the symlink
praxis-sv status --root /mnt/praxis   # operate against an installed target
```

`enable`/`disable` refuse to touch a path that exists but isn't a symlink,
so a hand-placed file under `/etc/service` won't be silently clobbered.

Praxis ships two services, both enabled by default:

- `shell` (`rootfs/etc/sv/shell/`): the interactive console. `run`
  execs `console`, which sets up the console device, runs desktop-session
  autostart when `praxis.live=0` is set and a desktop session is
  configured, and falls back to an interactive shell (`PS1='praxis# '`)
  either way. Desktop autostart stays inline here rather than becoming its
  own service, since it is inherently console-exclusive with the shell —
  splitting it would require real VT-switching logic runit doesn't provide
  for free.
- `udev` (`rootfs/etc/sv/udev/`): starts `systemd-udevd` when present,
  runs a one-shot `udevadm trigger`+`settle`, then holds the service alive
  so `runsv` doesn't restart-loop a daemon that intentionally detaches. On
  images without `systemd-udevd` (the default live ISO), it degrades to a
  no-op sleep rather than failing.

Adding a new service means adding a new `rootfs/etc/sv/<name>/run`
(executable, `exec`s its real process) — `praxis-sv enable <name>` (or a
default-enabled symlink staged the same way `shell`/`udev` are) makes
`runsvdir` pick it up, no other registration step required. There is no
choice-catalog layer for services yet (mirroring `config/choices/kernel/`
and `config/choices/init/`) — `praxis-sv` is a direct enable/disable tool,
not a profile picker. That richer catalog is still future work.

## Package Rule

Packages are chosen through explicit bundles, desktop profiles, and package
IDs. Praxis can list and show those choices. It must not silently decide a
desktop or package set.

Package catalogs are also manifest input. The v2 checks reject empty package
lists, invalid package tokens, and duplicate entries inside one profile. That
keeps the catalog sharp without pretending it is a beginner-friendly resolver.

## Manifest Rule

Base-system manifests are audits, not recipes.

```bash
praxis-manifest list
praxis-manifest show base-system
praxis-manifest verify base-system /mnt/praxis
```

`verify` reports missing files, directories, or links from the selected target.
It does not create them. A failed manifest check means the operator must inspect
the target and decide the next command.

## Provenance Rule

Praxis images must carry build evidence.

`/etc/praxis/build-info` records the build epoch, UTC date, git commit, dirty
state, and artifact hashes. `/etc/praxis/rootfs.sha256` records staged rootfs
file hashes.

```bash
praxis-provenance /mnt/praxis
praxis-provenance verify /mnt/praxis
```

Reproducible builds use the standard explicit knob:

```bash
export SOURCE_DATE_EPOCH=1700000000
make iso
```

Praxis honors that timestamp in build metadata and initramfs file mtimes. ISO
sidecars include `build/praxis.iso.build-info` and `build/praxis.iso.sha256`.
The operator still owns comparing artifacts across machines.

## Contract Rule

Contracts are portable evidence bundles, not restore scripts.

```bash
praxis-contract export /mnt/praxis > praxis.contract
praxis-contract inspect praxis.contract
praxis-contract verify praxis.contract /mnt/praxis
```

The contract records selected choices and hashes for important Praxis files
such as `system.choice`, `packages.selected`, `build-info`, `rootfs.sha256`,
seed ledgers, manifest ledgers, and the boot entry. `verify` checks that the
target still matches the exported bundle. It does not apply, repair, or restore
anything.

## Seed Rule

Seeding must not become a hidden installer.

A seed line is one explicit filesystem operation:

```text
mkdir /etc/praxis
write /etc/praxis/seed-profile v2-half
append /etc/motd Praxis v2-half seed applied.
```

The operator can dry-run the ledger before touching a target:

```bash
praxis-seed list
praxis-seed show base
praxis-seed --dry-run /mnt/praxis
```

Then apply it:

```bash
praxis-seed /mnt/praxis
```

## Still Not Done

The remaining v2 work is richer kernel/init profile build mechanics. The
current repo has most of the v2 contract shape: choice catalogs, seed
ledgers, manifest audits, recovery ledgers, v2 docs, and v2 validation.
